# down 的完整调用分项与因果对照

2026-10-18。此目录记录删除数值扫描、改用 FP16 激活之前的 revision6 诊断。固定大核2.4GHz、CPU4线程/0xf0、NPU1GHz/mask7、DDR2112MHz，使用刚重新调优的 M256 up/down 配置。原始数据见 [summary.json](summary.json)。

## 主要发现

down/up 约两倍的主要净差距来自 down 的 CPU 输入处理。down 先单线程 FP32→FP16，再单线程扫描 FP16 Inf/NaN，再通过通用逐元素循环打包 K 分块。up 走四线程融合转换/打包与结果收集。

| 分项，M256，单位ms | up | down |
|---|---:|---:|
| FP32→FP16 转换 | 包含于融合输入 | 0.322 |
| 转换后的单线程 Inf/NaN 扫描 | 包含于融合输入 | 0.960 |
| 分块输入打包 | 包含于融合输入 | 0.594 |
| 融合输入，总计 | 0.174 | — |
| 输入同步 | 0.060 | 0.164 |
| GEMM，含 submit/wait | 0.824 | 1.158 |
| NPU FP16 Add tree | — | 0.279 |
| 输出同步 | 0.146 | 0.037 |
| unpack 到紧凑 FP16 | 包含于融合输出 | 0.070 |
| widening + bias | 包含于融合输出 | 0.076 |
| 输出的单线程 Inf/NaN 扫描 | 包含于融合输出 | 0.278 |
| 融合输出，总计 | 0.729 | — |
| 整次调用 | 1.940 | 3.948 |

分项分别取中位数，不保证精确相加为整次调用中位数。down 的输入转换/扫描/打包合计约1.876ms，up 融合输入约0.174ms；约1.70ms 的输入净差，占约2.01ms整次调用净差的85%。单独两遍数值扫描约1.238ms，占 down 完整调用约31%。归约约占7%。

up GEMM 的驱动硬件区间约0.812ms，down约1.141ms；对应约2.645T与1.882T有效算力。此处是 GEMM 驱动区间口径，不是完整调用的 MFU，也不是 MAC busy cycles。

## 设备上发生的操作

down 的4个 K1024 partial 在一次 GEMM submit 内执行，共8个 task，三核分配3/3/2。随后 Add tree 有两次 submit：4→2 使用mask3、两核各1个task；2→1使用mask1、单核1个task。没有把4个 K 块拆成4次 GEMM submit。

输入为4MiB紧凑 FP32，经转换得到2MiB FP16，再打包成2MiB分块设备输入。常驻 B 为8MiB，上传不在计时内。四个 FP16 partial 合计2MiB，在设备归约后只同步最终512KiB输出，再 unpack、widen、加bias。每次调用没有将所有 partial 拷回CPU求和。

## 控制实验

将 task M cap128改成88，使 GEMM task 变成12个、三核4/4/4，GEMM反而约1.158→1.288ms；完整调用约4.073ms。N tile改成352后，任务数24、三核8/8/8，GEMM约1.655ms、完整调用4.423ms。因此单纯均衡更多 task 没有收益。

完整 K 参考配置的 GEMM约5.000ms，K分块后的约1.158ms；完整调用约5.955→3.948ms。K tiling 确实解决了原大 K 设备执行问题，但 CPU 转换/打包消耗了其中一部分收益。

## 只在诊断库内的局部替换

这些实验在相同固定几何和相同数学精度下分别替换 CPU 实现。数值检查仍保留：转换实验将检查融合进 NEON 转换并行循环；打包实验用连续行拷贝替换逐元素写入。基线与变体按进程级 ABBA，各有4个进程；每进程对各case预热后测16次完整调用。

| 诊断替换 | 对应配对基线 | 变体 | 时延下降 |
|---|---:|---:|---:|
| 仅向量化并行转换/检查，M256 | 3.938ms | 2.967ms | 24.65% |
| 仅分块输入行拷贝，M256 | 3.964ms | 3.612ms | 8.88% |
| 两项合并，M256 | 3.949ms | 2.630ms | 33.41% |
| 两项合并，M1024 | 14.864ms | 9.678ms | 34.89% |

M256两项合并后，up约1.950ms，down/up约1.35倍。GEMM硬件区间和归约时间基本不变，支持 CPU 输入处理是主要净差来源的判断。这些是单算子结果，不是已兑现的 ViT 加速。

后续用户明确要求删除运行时逐元素数值扫描，并要求 ViT 中间张量改为 FP16、norm/softmax 内部保留 FP32 累加；当前源码已继续推进，不应把本目录诊断原型当作当前默认实现。

## 验证与复现

插桩基线与冻结未插桩库的配对差：up约+0.46%，down约-0.76%。分项用于归因，绝对性能以未插桩整次调用为准。所有case在同进程内每次输出逐位一致，不同库的同一case完整输出哈希一致，并经过128个独立双精度dot-product oracle点检查。该测试不代替模型任务精度验证。

共40个精细计时/局部替换进程；M256与M1024的6类case均覆盖。同一进程的重复调用不视为独立进程样本。两个runner返回0、恢复错误为空，CPU/NPU/DDR频率边界与governor恢复通过。没有观察到submit/sync错误。

`profile-refined/`与三个`ablation-*/`保存了精确插桩源码、原始两个源文件、源哈希及模式。复现工具位于`scripts/diagnostics/build_fp16_stage_trace.py`、`fp16_stage_trace.{h,cpp}`和`fp16_stage_probe.cpp`；构建器的字符串定位对应本目录保存的revision6源码，使用`--source-snapshot llm_generated_docs/evidence/fp16_down_stages_20261018/profile-refined`选取原始源文件。冻结二进制/对象文件留在板端`/home/firefly/mnt/3090x4/tmp/fp16-down-stages-20261018/`。
